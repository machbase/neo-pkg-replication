## 2. 논리적 충돌 및 모순

### 2.1 [높음] 컬럼 규칙의 적용 범위 불일치

**요구사항 명세 섹션 4** (공개용):
> "다음 규칙은 Database의 기본 제약 사항이다. 데이터 테이블의 1번째 컬럼은 tag 컬럼이다."

**내부 설계 전제 섹션 3.1** (개발자용):
> "다음 컬럼 규칙은 Tag 테이블에만 적용되는 고정 전제이다."

**충돌**: 요구사항 명세는 컬럼 규칙을 모든 데이터 테이블의 일반 규칙처럼 기술하지만, 실제로는 Tag 테이블에만 해당합니다. Log 테이블은 컬럼 규칙이 없습니다(내부 설계 3.2에서 확인).

**영향**: 요구사항 명세만 읽은 구현자가 Log 테이블에도 컬럼 검증을 적용할 수 있음.

**제안**: 요구사항 명세 섹션 4에 "본 규칙은 Tag 테이블의 데이터 테이블에만 적용된다"를 명시하거나, 섹션 앞에 테이블 유형별 분리를 먼저 기술.

---

### 2.2 [중간] start_mode "full"의 시작 _rid 정의 불명확

**요구사항 명세 8.1**:
> "full : 최소 _rid부터 복제"

**상세설계 4.2**:
> "full: 최소 rid부터(구현상 start_rid=-1 또는 0)"

**문제**: "최소 _rid"가 실제 테이블의 min(_rid)인지, 0인지, -1인지 정의되지 않음. 상세설계에서도 "-1 또는 0"으로 확정하지 않음.

**제안**: `full`의 start_rid를 명확히 확정 (예: `start_rid = 0`, 또는 `start_rid = -1`로 DB가 최소 rid부터 반환하도록).

---

### 2.3 [중간] 메타 동기화의 범위 충돌

**요구사항 명세 3.1** (포함 범위):
> "메타 정보 동기화"

**상세설계 2.4**:
> "메타 동기화는 복제 루틴과 분리(별도 루틴/프로세스)"

**문제**: 요구사항에서는 메타 동기화가 시스템 범위에 포함되지만, 상세설계에서는 별도 루틴으로 분리. 별도 루틴의 설계가 문서 어디에도 없음.

**제안**: 메타 동기화의 구체적 동작(주기, 트리거, 동기화 방향)을 명세에 추가하거나, "1차 범위에서는 캐시 기반 조회만 수행, 별도 동기화 루틴은 후속 범위"로 명확히 구분.

---

### 2.4 [낮음] 체크포인트 파일명과 내용 불일치 시 처리 모호

**체크포인트 포맷 섹션 3**:
> "source.data_table은 파일명과 반드시 동일해야 함. 불일치 시 파일 내용이 우선"

**문제**: "반드시 동일해야 함"과 "불일치 시 내용 우선"이 모순. 불일치가 발생하면 안 되는 것인지, 발생하면 내용을 쓰는 것인지 혼재.

**제안**: 불일치 시 동작을 하나로 확정. 예: "불일치 시 경고 로그 출력 후 파일 내용 기준으로 동작" 또는 "불일치 시 손상으로 간주".

## 3. 결점 및 미정의 항목

### 3.1 [높음] servers 접속 문자열 형식 미정의

설정 예시:
```yaml
servers:
  srcA: "db-a.internal:1234"
```

host:port만 표기되어 있으며 **인증 정보(user, password)** 포함 방식이 정의되지 않음.

**제안**: 접속 문자열 형식을 명확히 정의. 예:
- URI 형식: `user:password@host:port`
- 또는 별도 인증 설정 블록 추가

---

### 3.2 [높음] 원본/대상 스키마 불일치 시 처리 미정의

요구사항:
> "대상 테이블 생성 및 스키마 관리는 제외 범위"

**문제**: 대상 테이블이 사전 생성되어야 하지만, 원본과 대상의 컬럼 수/타입이 다를 때의 동작이 정의되지 않음.
- Tag 테이블: tag_id → tag_name 변환으로 1번째 컬럼 타입이 바뀜. 나머지 컬럼은?
- Log 테이블: "그대로 전달"인데, 컬럼 수가 다르면?

**제안**: 스키마 불일치 감지 시점(DISCOVER 단계)과 처리 정책(mapping 스킵 등)을 명시.

---

### 3.3 [높음] Graceful Shutdown 정책 미정의

실행 중 시스템 종료(SIGTERM 등) 시:
- 진행 중인 배치는 완료 후 종료인지, 즉시 중단인지
- 체크포인트는 저장하는지
- 연결 정리 순서

상세설계의 상태 머신에 STOPPED 상태는 있으나 전이 조건이 없음.

**제안**: STOPPED 진입 조건 및 종료 시 배치/체크포인트 처리 정책 추가.

---

### 3.4 [중간] 다중 Worker 동시성 모델 미정의

상세설계:
> "1 data_table = 1 worker"

**문제**: 하나의 job 내 여러 data_table(예: _TAG_DATA_0 ~ _TAG_DATA_3)에 대해:
- Worker들이 동시(concurrent) 실행되는지?
- 순차 실행인지?
- 동시 실행 시 공유 자원(메타 캐시, DB 연결) 관리 방식은?

**제안**: Worker 동시성 모델을 명시. 예: "data_table별 worker는 병렬 실행. 메타 캐시는 공유. DB 연결은 worker별 독립."

---

### 3.5 [중간] retry 대상 판별 기준 미정의

요구사항:
> "재시도 불가 오류(설정 오류, 규칙 위반 등)는 해당 매핑을 실패 처리하고 스킵한다."

상세설계:
> "1차에서 raw 기록 우선, 에러 코드 세분 분류를 강제하지 않음"

**문제**: "재시도 가능"과 "재시도 불가"를 어떤 기준으로 구분하는지 정의되지 않음. 에러 코드 분류를 1차에서 강제하지 않으면 모든 에러가 retry 대상이 될 수 있음.

**제안**: 최소한의 분류 기준 제시. 예:
- 네트워크/연결 오류 → retry
- QueryError 중 특정 코드 → retry 불가 (설정 오류, 테이블 미존재 등)

---

### 3.6 [중간] checkpoint 저장 실패 시 정책 미확정

상세설계 SAVE_CHECKPOINT:
> "checkpoint 저장 실패는 운영상 심각하지만, 1차 정책은 '계속 진행' 또는 '중단' 중 선택 가능"

**문제**: 확정되지 않음. "계속 진행"이면 다음 재시작 시 대량 중복 발생, "중단"이면 한 번의 I/O 실패로 전체 복제 정지.

**제안**: 정책 확정. 예: "N회 연속 실패 시 mapping 중단, 그 외에는 경고 로그 후 계속"

---

### 3.7 [낮음] Log 테이블 n:1 매핑 시 데이터 구분 불가

요구사항 섹션 6 (Tag name 충돌 방지)은 Tag 테이블만 다루며, Log 테이블은 tag_identifier가 없음.

**문제**: 여러 원본 Log 테이블이 하나의 대상으로 복제될 때, 데이터 출처를 구분할 방법이 없음.

Backlog 7.2에 `log.identifier_columns` 확장이 언급되어 있으나, 현재 범위에서 n:1 Log 매핑이 허용되는지 자체가 불명확.

**제안**: 1차 범위에서 Log 테이블은 1:1만 허용하거나, n:1 시 구분 불가에 대한 경고를 명시.

---

### 3.8 [낮음] 설정 핫 리로드 여부 미정의

실행 중 설정 파일 변경 시:
- 자동 감지 및 반영(hot reload)?
- 프로세스 재시작 필요?
- 매핑 추가/제거 시 기존 작업 영향은?

**제안**: 1차 범위에서는 "프로세스 재시작 필요"로 명시.

## 4. 설계 개선 제안

### 4.1 execution 설정 3단계 우선순위 — 위치 정리 필요

현재 스키마에서 `execution` 블록이 3곳에 배치 가능:
1. `job.execution_defaults` (job 레벨 기본값)
2. `mapping.source.execution` (source 레벨)
3. `mapping.execution` (mapping 레벨)

설정 예시에서 mapping-level `execution`이 `source`/`target`과 동일 레벨에 위치하여, `source.execution`과의 관계가 직관적이지 않음.

**제안**: 2단계로 단순화하거나, 3단계를 유지한다면 각 레벨의 용도 차이를 예시와 함께 명확히 기술.

---

### 4.2 STARTUP_INTEGRITY에서 safe_cp_rid = row.rid - 1 경계값 처리

의사코드:
```
safe_cp_rid = row.rid - 1
```

row.rid가 0이면 safe_cp_rid = -1이 됨. -1이 유효한 체크포인트 값인지 별도 정의가 없음.

**제안**: _rid 최소값과 checkpoint 초기값의 관계를 명확히 정의.

---

### 4.3 모니터링/헬스체크 인터페이스 부재

현재 관측성은 로그 기반만 존재. 운영 환경에서 필요한 항목:
- job/mapping/worker별 현재 상태 조회
- 현재 처리 중인 _rid 범위
- 에러/retry 카운트
- 마지막 체크포인트 시각

**제안**: 1차에서는 구조화 로그로 대응하되, 향후 상태 조회 API 또는 메트릭 내보내기(Prometheus 등) 확장 가능하도록 내부 상태 모델을 설계.

---

### 4.4 배치 크기와 메모리 제한 관계 미정의

`batch_size_records`가 설정으로 노출되지만, row당 크기 제한이 없어 극단적인 경우 메모리 초과 가능.

**제안**: `batch_size_bytes` 상한 또는 row당 최대 크기 경고 정책 고려.

---

## 5. 문서 품질 관련 의견

### 5.1 문서 간 중복 기술이 많음

동일 내용(컬럼 규칙, 체크포인트 정책, Tag/Log 분리 등)이 5개 섹션에 반복 기술됨. 표현이 미묘하게 달라 위 2.1과 같은 해석 차이를 유발.

**제안**: 정의는 한 곳에서만 하고, 나머지는 참조 형태로 구성. 예: 상세설계를 단일 진실의 원천(single source of truth)으로 삼고, 다른 문서는 요약+참조.

### 5.2 확정/미확정 사항 구분이 명확

"확정" 표기, Backlog 분리 등 의사결정 상태가 잘 구분되어 있음. 이 점은 문서 품질로서 매우 양호.
